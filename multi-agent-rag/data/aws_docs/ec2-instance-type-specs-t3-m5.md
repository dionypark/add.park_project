## T3 패밀리 — 버스터블 성능 (일반적인 소규모 웹서버/파일럿/개발 환경에 적합)

T3는 평소엔 기준 성능(baseline)보다 낮게 쓰다가, CPU 크레딧을 모아뒀다가 트래픽이 몰릴 때 순간적으로
더 높은 성능을 낼 수 있는 인스턴스 타입이다. 상시 고성능이 필요 없고 트래픽이 간헐적인 워크로드(소규모
API 서버, 개발/테스트 환경, 파일럿 테스트)에 적합하다. GPU는 없다 — 순수 CPU/메모리 자원만 제공한다.

| 인스턴스 타입 | vCPU | 메모리(RAM) | 네트워크 성능 | 적합한 용도 |
|---|---|---|---|---|
| t3.nano | 2 | 0.5 GiB | 최대 5 Gbps | 아주 가벼운 스크립트, 극소규모 테스트 |
| t3.micro | 2 | 1 GiB | 최대 5 Gbps | 프리티어, 아주 작은 정적 사이트 |
| **t3.small** | **2** | **2 GiB** | 최대 5 Gbps | **소규모 파일럿 테스트, 가벼운 API 서버 1~2개 정도 (지금 이 프로젝트가 쓰는 사이즈)** |
| t3.medium | 2 | 4 GiB | 최대 5 Gbps | 임베딩 모델처럼 메모리를 좀 더 쓰는 서비스, 소규모 프로덕션 |
| t3.large | 2 | 8 GiB | 최대 5 Gbps | 트래픽이 좀 더 있는 서비스, DB+API 같이 운영 |
| t3.xlarge | 4 | 16 GiB | 최대 5 Gbps | 중간 규모 애플리케이션 서버 |
| t3.2xlarge | 8 | 32 GiB | 최대 5 Gbps | 무거운 배치 작업, 여러 서비스 동시 운영 |

**t3.small 관련 운영 팁**: RAM이 2GiB로 빠듯해서, Docker + 여러 프로세스(FastAPI+Streamlit 등)를 같이
띄우면 메모리 부족(OOM)이 날 수 있다. swap 메모리를 추가로 설정해두는 걸 권장한다 (본문 서버 운영 관련
질문 참고). CPU도 "버스터블"이라 평소엔 기준 성능만 나오고, CPU 크레딧이 바닥나면 속도가 느려질 수
있다 — 지속적으로 CPU를 많이 쓰는 작업(대량 배치 처리 등)엔 안 맞고, 간헐적 트래픽에 적합하다.

## T3 "CPU 크레딧" 메커니즘 자세히

T3가 왜 저렴한지, 언제 성능이 떨어질 수 있는지 이해하려면 크레딧 시스템을 알아야 한다.

- **베이스라인 성능**: 각 T3 사이즈는 vCPU당 "이 정도 사용률까지는 계속 무제한으로 쓸 수 있다"는 기준선이
  있다. 사이즈가 클수록 베이스라인도 높다 — 대략 t3.nano/micro는 vCPU당 5~10%, t3.small/medium은
  20%, t3.large는 30%, t3.xlarge 이상은 40% 수준(정확한 수치는 인스턴스 세대/AWS 발표 기준으로 소폭
  달라질 수 있음).
- **크레딧 적립/소비**: 베이스라인 밑으로 쓰면(예: CPU를 5%만 쓰는 중) 그 여유분만큼 크레딧이 쌓인다.
  베이스라인을 넘겨서 써야 할 때(트래픽 몰릴 때) 쌓아둔 크레딧을 소비해서 순간적으로 100%까지 성능을
  끌어올린다(버스트).
- **크레딧 고갈 시**: 쌓아둔 크레딧을 다 쓰면, 그 이후로는 베이스라인 성능으로 강제로 떨어진다(먹통은
  아니고 "느려짐"). 지속적으로 CPU를 많이 쓰는 워크로드(상시 고부하 배치 작업 등)는 크레딧이 계속
  고갈 상태라 오히려 손해일 수 있다.
- **T3 Unlimited 옵션**: 크레딧이 바닥나도 성능을 안 떨어뜨리고 그냥 추가 요금을 내고 베이스라인 이상
  성능을 계속 쓰는 옵션. 트래픽이 언제 몰릴지 예측이 어려운 파일럿/프로덕션 초기 단계에서 성능 저하로
  장애 나는 것보다 안전하게 켜두는 경우가 많다(추가 비용은 초과 사용량에 비례, 미미한 수준일 때가
  많음).

## 워크로드/프레임워크별 최소 권장 사이즈 (일반적인 가이드라인)

"내 앱엔 뭘 써야 하나"에 대한 실전 기준. 정확한 필요 사양은 실제 부하 테스트로 확인하는 게 정석이지만,
아래는 일반적으로 통용되는 최소 권장선이다.

| 사이즈 | 적합한 워크로드 | 주의사항 |
|---|---|---|
| t3.micro (1GiB) | 단순 정적 웹서버(Nginx), 가벼운 Node.js/Express API, Go/Rust 서버 | Java/Spring Boot는 빌드/구동 시 메모리 부족(OOM)으로 다운되기 쉬움 |
| **t3.small (2GiB)** | **Spring Boot 기본 애플리케이션 최소 권장선**, Docker 컨테이너 2~3개 동시 실행(API+Redis+Nginx 등), 소규모 React 빌드/테스트 | 그래도 빠듯함 - swap 설정 권장, 동시에 여러 개 무거운 프로세스 띄우면 OOM 위험 |
| t3.medium (4GiB) | DB+백엔드를 한 서버에 같이 테스트, PyTorch/TensorFlow CPU 추론(경량 모델), 데이터 가공 배치 작업 | GPU 추론은 이 패밀리로 불가능(T3는 GPU 없음, 딥러닝 학습/대형 모델 추론엔 별도 GPU 인스턴스 필요) |
| t3.large 이상 (8GiB+) | 여러 서비스를 한 서버에 몰아서 운영, 중간 규모 빌드 서버 | 이 정도부턴 M5(범용) 패밀리와 비용 비교해보고 선택 권장 |

## M5 패밀리 — 범용 (안정적인 성능이 꾸준히 필요한 프로덕션 서비스에 적합)

M5는 T3와 달리 크레딧 소진 걱정 없이 항상 일정한 성능을 낸다. 상시 트래픽이 있는 프로덕션 서비스,
데이터베이스, 캐시 서버 등에 적합하다. T3보다 시간당 요금은 비싸지만, 성능이 예측 가능하다.

| 인스턴스 타입 | vCPU | 메모리(RAM) | 네트워크 성능 | 적합한 용도 |
|---|---|---|---|---|
| m5.large | 2 | 8 GiB | 최대 10 Gbps | 소규모 프로덕션 API 서버 |
| m5.xlarge | 4 | 16 GiB | 최대 10 Gbps | 중간 규모 프로덕션 서비스 |
| m5.2xlarge | 8 | 32 GiB | 최대 10 Gbps | 트래픽이 많은 서비스, 중간 규모 DB |
| m5.4xlarge | 16 | 64 GiB | 최대 10 Gbps | 대규모 애플리케이션, 무거운 연산 |

## T3 vs M5 — 언제 뭘 골라야 하나

- **트래픽이 간헐적이고(하루 종일 놀다가 가끔 몰림) 예산이 중요하면** → T3 (버스터블, 저렴)
- **트래픽이 꾸준하고 일정한 성능이 보장돼야 하면(DB, 결제 서버 등)** → M5 (범용, 안정적)
- **지금 이 프로젝트(가늠) 같은 일주일짜리 파일럿 테스트, 사용자 소수** → T3 계열(t3.small~medium)로 충분,
  M5까지는 오버스펙인 경우가 많음
